## 八、台账维护规则

1. **每次代码改动后追加一条**，格式见「二」，字段不全的留空，不删历史。
2. **不覆盖**：已被取代的变更在「六」标注，不在原条目上改写。
3. **可追溯**：每条必须带 commit SHA；非代码交付物必须带文件路径。
4. **验证必须写明基线数字**（如 `17/17`），不写「测试通过」这种不可核对的结论。
5. **局限与已知缺陷必须写进条目**，不藏在别处（如 P6 内存桶的冷启动重置）。
6. **数字必须带快照时点**；仓库活跃时「总数」类数字不做永久承诺。
7. **每条必须有「修改人」署名**，取自 git 的 `author` 字段，不得自拟。
   - 直接提交：写提交作者
   - **合并类条目必须双署名**：`实施` = 被合入提交的作者；`整合 / 记录` = 做合并的人
   - 署名用 git 里的完整 `名字 <邮箱>`，便于与提交历史交叉核对
8. **新条目编号前先查重**：往「二」加条目前，先搜一遍现有 `### 变更 #N`，
   避免两个并行修改者撞同一个编号（本项目已实际发生过：main 与分支同时用了「变更 #7」）。
   建议新条目用「#N+1」取当前最大编号 +1，而不是各自起算。
9. 台账本身纳入版本管理，随代码一同提交（已由 `scripts/check-ledger.js` 在 CI 强制执行）。
